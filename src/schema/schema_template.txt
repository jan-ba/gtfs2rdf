/*
================================================================================
gtfs2rdf — Schema Template (NOT COMPILED)
================================================================================

Drop this file somewhere that is NOT picked up by your build (e.g. src/schema/schema_template.txt).
Copy-paste it into a new *.cppm schema file when you want to add a schema.

This template follows your current gtfs2rdf "schema file" structure:
  - one exported build<Name>Schema(...) function that returns schema::Schema
  - a list of POSSIBLE_COLUMNS (for header validation / column lookup)
  - a PREFIXES map (used for Turtle PREFIXES and CURIE expansion)
  - a vector of rdf::Triple entries with placeholder instructions
  - OPTIONAL: a vector<string> side_effects (placeholder-instructions that DO NOT write to file)

-------------------------------------------------------------------------------
1) Placeholder syntax inside strings
-------------------------------------------------------------------------------
In any instruction string, `{...}` marks a placeholder that is filled from the Gtfs row.

A placeholder has this general form:

    { arg1,arg2,... | transformA | transformB | ... }

Rules:
  - whitespace inside the braces is removed.
  - args BEFORE the first '|' are comma-separated "arguments".
  - transforms are chained with '|'. (MAX_TRANSFORMS is currently 3.)
  - MAX_ARGS is currently 9.

-------------------------------------------------------------------------------
2) Transform kinds: Transform2One vs Transform2Many
-------------------------------------------------------------------------------
Transform2One:
  - signature: void(const ArgSpan& args, std::string& out)
  - produces a single output string (c)

Transform2Many:
  - signature: void(const ArgSpan& args, std::vector<std::string>& out)
  - produces multiple outputs and duplicates the rendered instruction over them
    (one per element in transf_buf_)

Important limitation (current implementation):
  - within ONE rendered instruction string, only ONE Transform2Many may appear in total.

Evaluation order:
  - transforms BEFORE a Transform2Many can take spanN (all args)
  - Transform2Many produces transf_buf_
  - transforms AFTER Transform2Many are applied element-wise to transf_buf_

-------------------------------------------------------------------------------
3) Storage write syntax (persistent storage)
-------------------------------------------------------------------------------
Storage writes are encoded directly in placeholders using '>'.

General forms:

(A) Variable store (no ':'):
    { value_expr | transforms... > CONST_NAME@ctx.txt }

  - Stores the final computed output of the transform chain as a VARIABLE.

(B) Keyed store (mapping) via ':':
    { key_fields : rhs_fields | transforms... > MAP_NAME@ctx.txt }

  - "key_fields" is a comma-separated list; the key is built from these fields.
  - "rhs_fields" are additional arguments available to transforms (e.g. date, exception_type),
    but are NOT stored raw unless you use (...) (see below).
  - Stored VALUE is the final computed output of the transform chain.
  - This is how you do: service_id -> [formatted_dates...]

(C) FilterStoreRaw via parentheses on the RHS:
    { key_fields : (value_fields...) , extra_fields... | transforms... > MAP_NAME@ctx.txt }

  - Parentheses mean: transforms act as a FILTER predicate (non-empty output => store raw).
  - Stored VALUE is the RAW tuple (value_fields...), not the computed transform output.
  - extra_fields... are available to transforms but not stored.

Notes:
  - A bijection key:value is NOT guaranteed (values are vectors) except for variables.
  - '@ctx.txt' denotes the storage context. If omitted, the current schema context is used.
  - Using '>' in a placeholder makes it a "side-effect placeholder": it writes to storage.
    Whether it also writes to FILE depends on the instruction target (see side_effects below).

-------------------------------------------------------------------------------
4) Side-effect instructions (no file output)
-------------------------------------------------------------------------------
Instead of using a fake triple like: { "", "", "{... > ...}" },
you can define side effects directly:

    const std::vector<std::string> side_effects = {
        "{ service_id : date, exception_type | some_filter | convertDate2xs_unchecked > disabled_dates@calendar_dates.txt }"
    };

These are processed like normal instruction strings, but are not written to the Rdf output.

-------------------------------------------------------------------------------
5) Triple structure
-------------------------------------------------------------------------------
A triple is: { SUBJ, PREDICATE, OBJECT }

  - SUBJ / PREDICATE are rdf::IRI
  - OBJECT is an rdf::Object, which can be:
      * a plain literal:           { "{field}" }
      * a language-tag literal:    { "{field}", "de" }
      * a typed literal:           { "{field}", IRI("xs","integer") }
      * an IRI object:             { IRI("gtfs","Stop") }

-------------------------------------------------------------------------------
6) Where to register transforms
-------------------------------------------------------------------------------
You can register transforms inside build<Name>Schema(...).
This is fine even with the new parser approach, as long as you:
  - build all used schemas first (registers transforms)
  - parse/compile instructions afterwards (needs registry populated)

================================================================================
*/

module;

#include "transform_macros.h"

#include <string>
#include <unordered_map>

export module schema:YOUR_SCHEMA_NAME;

import :core;
import rdf_components;
import field_transforms;
import t_lib;
import runtime;

using namespace rdf;

namespace schema {

// =============================================================================
// 1) OPTIONAL: schema-local example transforms
// =============================================================================
namespace example_transforms {

// Transform2One example: lon,lat -> WKT POINT(lon lat)
void wkt_point_lon_lat(const field_transforms::ArgSpan& args, std::string& out) {
  if (args.size() != 2) {
    throw std::runtime_error("wkt_point_lon_lat: expected 2 args (lon,lat)");
  }
  const auto& lon = args[0];
  const auto& lat = args[1];
  if (lon.empty() || lat.empty()) return;
  out = "POINT(" + lon + " " + lat + ")";
}

// Transform2Many example: split on ';'
void split_semicolon(const field_transforms::ArgSpan& args,
                     std::vector<std::string>& out) {
  if (args.size() != 1) {
    throw std::runtime_error("split_semicolon: expected 1 arg");
  }
  const std::string& s = args[0];
  std::string cur;
  for (char ch : s) {
    if (ch == ';') {
      if (!cur.empty()) out.push_back(cur);
      cur.clear();
    } else {
      cur.push_back(ch);
    }
  }
  if (!cur.empty()) out.push_back(cur);
}

} // namespace example_transforms


// =============================================================================
// 2) REQUIRED: build function
// =============================================================================
export Schema buildYourSchemaNameSchema(runtime::RuntimeContainer& rtc) {

  // ---------------------------------------------------------------------------
  // (A) Register transforms (schema-local + shared)
  // ---------------------------------------------------------------------------
  rtc.getTransformRegistry().registerTransform("wkt_point", example_transforms::wkt_point_lon_lat);
  rtc.getTransformRegistry().registerTransform("split_semicolon", example_transforms::split_semicolon);

  // ---------------------------------------------------------------------------
  // (B) Columns that may appear in the Gtfs file header
  // ---------------------------------------------------------------------------
  const std::vector<std::string> POSSIBLE_COLUMNS = {
    "id",
    "name",
    "lon",
    "lat",
    "tags"
  };

  // ---------------------------------------------------------------------------
  // (C) Prefixes (Turtle expansion)
  // ---------------------------------------------------------------------------
  const std::unordered_map<std::string, std::string> PREFIXES = {
    { "ex",   "https://example.org/resource/" },
    { "rdf",  "http://www.w3.org/1999/02/22-rdf-syntax-ns#" },
    { "xs",  "http://www.w3.org/2001/XMLSchema#" },
    { "gtfs", "https://w3id.org/gtfs2rdf#" }
  };

  // ---------------------------------------------------------------------------
  // (D) Subject IRI template
  // ---------------------------------------------------------------------------
  const IRI SUBJ = IRI("ex", "{id}");

  // ---------------------------------------------------------------------------
  // (E) Triples (file output)
  // ---------------------------------------------------------------------------
  const std::vector<Triple> TRIPLES = {
    { SUBJ, {"rdf","type"}, { IRI("gtfs","YourClass") } },
    { SUBJ, {"gtfs","name"}, { "{name}" } },
    { SUBJ, {"gtfs","wktPoint"}, { "{lon,lat|wkt_point}" } },
    { SUBJ, {"gtfs","tag"}, { "{tags|split_semicolon}" } },
  };

  // ---------------------------------------------------------------------------
  // (F) Side effects (storage only, no file output)
  // ---------------------------------------------------------------------------
  //
  // NOTE: This is intentionally a vector<string> and NOT rdf::Triple.
  // The engine can parse+execute these placeholders for each row, but does not
  // append anything to the Rdf writer.
  //
  // Example (keyed computed store): id -> formatted(name) only if some filter returns non-empty
  //   "{ id : name | my_filter | my_format > some_map@your_schema_name.txt }"
  //
  const std::vector<std::string> side_effects = {
    // Put schema-local storage instructions here, if needed.
  };

  // ---------------------------------------------------------------------------
  // (G) Build Schema object
  // ---------------------------------------------------------------------------
  // CHANGE: Schema now also accepts side_effects (new field) so you can avoid fake TRIPLES.
  Schema sch("your_schema_name.txt", POSSIBLE_COLUMNS, PREFIXES, TRIPLES, side_effects, rtc);
  return sch;
}

} // namespace schema


For updated version of template:
- It should be rather concise such that it can be read easily
- stress that indexed access via operator [] to ARGS is not bound-checked, if a user wants that
  then they should check size of span first and in case of anything wrong (not enough args etc.)
  throw a custom exception via makro (explain the usage of that as well as the TRANSFORM2X makro usage)
- TRANSFORM2X {} TRANSFORMEND, here the curly braces are not required they help however with formatting
  from clang-format, hence they are to be desired (this shouldnt be explained technically, rather
  the user should just use these)
- there are a few library transforms available, for these, the user should check out transform_lib.cppm
- all usages of the placeholder syntax should be nicely explained as well as a few hints regarding
  usage of the storage 
- stress that storage-only instructions are always executed before all non-storage-only instructions 
  (i.e. triple generation instructions)
- several argument types are supported: column from the file row, literal (in \", important that " are escaped)
  and storage variables via <var_name>@<context_name ending in .txt>
